## 0. 整体叙事主线

从痛点出发，以治理筑基、统一底座、分时驱动、智能消费、分析增强、价值闭环，构建可持续的智能数据中枢体系。

胶片叙事按 8 段推进：

1. 数据孤岛与成本之痛
2. 数据治理
3. 统一数据湖仓底座
4. 分时数据处理引擎
5. 面向智能应用消费
6. 智能化探索与智能分析
7. 降本增效与价值量化
8. 三年产品规划

各章结构：**目标 → 场景 → 实践 → 下一步计划**。页脚为蓝色横幅。

**核心定位：** 面向 6G 演进（AI-Native、海量 UE 级数据、跨域共享），把「数据引擎」升级为「智能数据中枢」。

**七大能力：**

1. 统一治理（Owner 制）
2. 统一湖仓底座
3. 分时处理（秒 / 分 / 小时级）
4. 分布式数据中枢 + 联邦查询

6. 智能问数（NL2SQL/API + 本体语义）
7. 降本量化（Zeno/Saturn 替代 AP、统一计算存储架构）

### 第 3 页 · ① 数据管控痛点

**导语（运维方式转变的本质）：**  
从基于网络小区的网络运维管理 → 基于网络+UE 级的网络运维分析；从多数据库 → **统一湖仓架构**，对数据做统一订阅 / 消费 / 数据协同性分析。

**架构现状：**  
生产者（基站）×n → 订阅 / 采集 / 存储 → 消费者（NGI 用户级分析、RDE 智能体专家、融合感知平台 3 大场景、NM+NIA FCAPS 应用）；采集通道 7 个（基站和 UME 通道 1..n）。

**左栏 7 条痛点（基站数据生产）：**

- **a.** 基站数据 / 模型不支持灵活扩展数据类型和消费场景
- **b.** 缺少面向智能应用的语义描述
- **c.** 基站生成数据不自洽（RCA 和 MR 数据）（后续映射表写作「不自治」，见第 5 页注）
- **d.** 数据订阅：不支持精准订阅
- **e.** *截图 03 止于 d、截图 04 起于 f，本条未完整露出*
- **f.** 基站通道：网元网管采集通道多（7 个）
- **g.** 数据投递：不支持一次采集、多方消费

**右表（数据存储形态多样，复用成本高）：**

| 数据类型 | 归属层次 | 存储形态 | 访问接口 |
|---|---|---|---|
| 配置 | 设备+小区级 | PG 数据库，高速缓存 Redis | RANCM 接口 |
| 工参 | 设备+小区级 | PG 数据库 | EPM 接口 |
| FM | 设备+小区级 | ES、PG 数据库 | OTAF FM 接口 |
| PM | 设备+小区级 | AP、Gbase 数据库 | OTAF PM 接口 |
| Metrics/画像 | 小区+UE 级 | 持久化卷 | DCM 订阅和 DCM 采集接口 |
| MR 等 UE 级数据 | 小区+UE 级 | 持久化卷 | DCM 订阅和 NDS 采集 |

**注：UE 级数据是小区级数据的 9 倍（存储成本痛点核心）。**

### 第 4 页 · ① 现有数据中枢管理架构现状

**架构：**  
生产者（基站×2、DPI）→ 数据管理框架 → 统一数据处理 / 数据中枢框架（订阅、采集、清理、存储、分发、开放）→ 消费者（NM+NIA FCAPS、RDE 智能体专家、融合感知三大场景、NGI 三大应用、IMind 跨域故障、IDA 感知分析）。

**痛点① 基础 / 核心能力不足**

- **数据采集：** 版本定制化采集；NDS 数据近实时采集能力不足
- **数据存储：** 单域数据孤立，技术栈不统一；**UE 级数据占比 90%，存储成本高**
- **数据处理：** 流、批处理端到端时延为小时级；UE 级与小区级数据孤立
- **数据消费：** 版本定制化开发方式
- **数据治理：** 缺少数据与硬件资源的统一管理；无治理手段 / 工具

**痛点② 面向 AI 能力不足，主要靠人主动运维**

- 缺乏统一数据模型和知识模型（无法支撑智能问数）
- 数据孤立、关联不足、缺少治理手段 → 无法满足 AI 可信要求，**Data4AI 能力不足**

**方向句：**  
转向 AI-Native 能力：数据引擎 → 数据中枢 → 智能数据中枢。  
新增诉求：可信数据产品、多维度数据质量洞察和治理、跨系统数据共享、分布式数据处理、数据语义。

### 第 6 页 · ② 数据 Owner 和数据质量治理

**目标：**  
让数据资产更全、更可信，运营更精准。

- **数据治理：** 建立统一数据模型并明确 Owner；Owner 负责发布数据规范、守护模型。
- **数据质量：** 覆盖模型、质量、存储、计算、安全 + 数据价值评估，形成数据资产。

**架构：**  
RDE 通算集群（支撑训练 / 推理、决策、数字孪生和闭环）+ 智算集群 + 数据中枢（统一湖仓，spark → zeno、saturn）+ 数据集成组件。  
数据源：NDS、UME-NM、网元、智算板、外部数据。  
Owner 图例：NIA（黄）、NGI（橙）、IDA（绿）、iMind（粉）。

**场景：**

- **网络优化智能体：** 依赖 5s 粒度 KPI/KQI 指标和特征数据，识别质差话单及根因。
- **波束空间大模型：** 依赖地图、天线、工参和 MR 数据，识别覆盖问题及根因。

**实践：**

- CM / PM / 工参 / MR 统一建模入湖（统一存储）。
- 波束空间大模型支持异厂商数据导入。
- 建设 saturn「穿刺」可观测指标。

**下一步计划：**

- 参照 CM/PM 建设后续入湖数据模型规范（7/11）。
- 支撑 CM/PM/FM 跨域共享场景的异厂商接入。
- 完成在湖数据在有效性、一致性、准确性、及时性、完整性、唯一性等维度的治理方案，并开展质量评估。

### 第 10 页 · ④ 分时数据处理机制（匹配差异化时延诉求）

**核心机制：** 三层分时，由不同组件承担，在数据新鲜度与资源开销之间折中。

| 层次 | 位置 / 时延 | 用途 | 说明 |
|---|---|---|---|
| 实时层 | 基站，秒级 | 实时监控、快控等立即响应 | 基于 6G 数据面穿刺，支撑基站自闭环 |
| 近实时层 | NDS，1 或 5 分钟 | 分钟级分析、「轻洞察」 | 支撑体验智能体 5 分钟内端到端时延监控 |
| 非实时层 / 批处理 | NGI，≥15 分钟 | 历史挖掘、模型训练、报表汇总 | 客诉端到端时延由小时级降到 30 分钟 |

**架构图（image64.png）：**  
智能基站 1–3（产生秒级实时数据）→ NDS1–3（业务合并与端到端汇总，1min/5min）→ NGI（应用、动态扩展二次清洗、Iceberg、数据清洗 + ADMA + 智能体 Kafka）→ 第三方。蓝色上向箭头贯穿数据流。

**场景：**

- 体验智能体：5 分钟 UE 级 KQI 监控
- 福州移动项目：用户画像数据对接（小时级）

**实践：**

- 用户画像数据 1 小时内完成对接，获客户认可
- 形成分层数据处理范式（外部数据时延 5 min / 1 min）

**下一步计划：** 将 NDS 处理能力登记到统一模型，支撑数据编排。

### 第 11 页 · ④ NDS 近实时能力提升，LTE RCA 能力上移

**目标：** NDS 作为网元适配层，补齐网元硬件与通信方式差异，推动上层应用统一运维机制。

**左下架构图（image65.png）：**

- **消费层：** NM(n) FCAPS；MDA(1)（网优 / 故障 / 性能 / 体验，ADS 订阅 / 模型 / 发布）；新合建模平台；NGI(n) 用户级分析
- **处理层（橙色「实时数据采集+分布式处理」）：** 统一订阅 / 建模 / 呈现、lead2sql、小根因链路挖掘
- **存储：** 一库一湖（数仓 DW / 数据湖 ODS）
- **采集层：** 分布式 NDS 采集层（DCM 平台 / 硬件 / B 场库 / 网元识别数据 / IMS 连接 / M 库应用）
- **生产者：** 2/3/4/5G 及 6G 基站（CPA/UPA/SPA/平台…）

**右下 RCA 流向：** 4G 基站 ×2（CDT 数据）→ NDS（BSO 解析）→ 上层 RDE / NGI / 智算管控（模型训练）。含 UE 级与小区级 RCA 上报。

**场景：**

- LTE 质差栅格根因分析：向 NGI 提供 UE 级质差根因
- LTE 质差小区根因分析：向 NQI 提供小区级质差根因
