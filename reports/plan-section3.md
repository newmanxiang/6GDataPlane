# 第三章胶片制作计划

## 一、制作目标

将 HTML 报告第三章的八项趋势压缩为 6 页高密度战略胶片，在不牺牲可读性的前提下，保留原文中真正具有判断价值的内容：

1. 趋势的准确定义；
2. 趋势成立逻辑；
3. 关键技术与运行机制；
4. 工程落地边界；
5. 领先信号与验证指标；
6. 反证条件；
7. 标准、厂商和商业证据状态。

胶片不逐句复制 HTML，而是将每项趋势组织为“判断—机制—边界—验证—证据”的统一结构。

## 二、总体叙事

第三章不再采用严格串行的“状态可知—数据适用—行动可信—价值可结算”表述，而采用以下产业结构：

> **可信数据供给底座 → 自动化动作可信准入 → 双路径价值实现；标准规则横向贯穿**

其中：

- T2/T3 解决分布式环境下的数据变化感知和近源运行；
- T1/T6 解决数据产品化和面向任务的适用性；
- T4/T5 解决智能决策进入真实网络后的责任与风险控制；
- T7 区分能力型服务和结果型服务两条商业路径；
- T8 判断上述能力最终以何种标准载体落地。

## 三、统一页面规范

### 3.1 信息结构

每项趋势固定保留以下内容：

| 信息层 | 需要回答的问题 |
|---|---|
| 趋势判断 | 未来将发生什么结构性变化？ |
| 机制定义 | 具体变化体现在哪些对象、流程和能力？ |
| 成立逻辑 | 为什么该趋势具有持续性？ |
| 落地形态 | 需要哪些组件、接口和运行机制？ |
| 适用边界 | 该趋势不能被扩大解释为什么？ |
| 验证体系 | 领先信号、指标和反证条件是什么？ |
| 证据状态 | 已有事实、研究主张和证据缺口分别是什么？ |

### 3.2 视觉编码

- 蓝绿色：可信数据供给底座；
- 橙色：自动化动作可信准入；
- 浅绿色：能力型服务；
- 深绿色：结果型服务；
- 灰蓝色：标准承载；
- 绿色标签：高确定性；
- 蓝色标签：中高确定性；
- 橙色标签：中等确定性；
- 灰色标签：低—中确定性。

### 3.3 版式要求

- 16:9 页面；
- 每页只设置一个结论型主标题；
- T 编号作为眉题或模块标签，不替代结论型标题；
- 每页只使用一张主结构图；
- 机制、边界和验证信息进入结构化卡片，不使用大段正文；
- 页脚保留证据来源，但不让厂商名称主导页面；
- “领先信号—验证指标—反证条件”使用统一底栏；
- 每项趋势的完整名称至少出现一次。

# 第 1 页｜趋势筛选与总体结构

## 眉题

> **第三章｜T1–T8 产业趋势总览**

## 主标题

> **从 R1–R8 到 T1–T8：6G 数据能力将形成“可信底座、动作准入、双路径价值、标准横切”的产业结构**

## 副标题

> 两类数据基础能力并行建设；高风险自动化扩权受到可信证据约束；能力型服务与结果型服务具有不同前置条件。

## 页面目标

同时回答两个问题：

1. T1–T8 是如何从第二章需求与产业证据中筛选出来的；
2. 八项趋势之间为什么形成当前依赖关系，而不是八条平行判断。

## 页面布局

```text
┌─────────────────┬────────────────────────────────┐
│ 左侧 25%        │ 右侧 75%                      │
│ 趋势筛选方法    │ T1–T8 依赖结构图              │
├─────────────────┴────────────────────────────────┤
│ 底部：八项趋势名称、确定性及主要证据状态         │
└──────────────────────────────────────────────────┘
```

## 左侧内容：趋势筛选方法

### 入选门槛

**需求刚性**

- 问题是否由 6G 的物理分布、AI 原生、跨域自治和生态开放等结构性变化产生；
- 如果不解决，该问题是否会持续限制数据使用、动作安全或商业规模。

**可证伪性**

- 是否能够设置领先信号；
- 是否能够定义可测试指标；
- 是否存在明确反证条件。

### 确定性判断

**工程成熟度**

- 是否已有组件、原型、参考架构或部署基础；
- 是否具备可实施的接口、运行时和治理机制。

**产业牵引力**

- 标准讨论、厂商投入、客户需求和商业信号是否同向；
- 证据属于规范事实、产品事实、研究主张还是愿景。

## 右侧内容：总体结构图

```text
T2 元数据事件化 ─────┐
T3 全局控制/近源执行 ├─ 可信数据供给底座
                     │
T1 可运营数据产品 ───┤
T6 任务适用性准入 ─────┘
          │
          ├────────→ T7 能力型服务路径
          │
          └→ T4 Agent 协同闭环
             T5 NDT 动作证据
                     │
                     └→ T7 结果型服务路径

T8：能力与接口优先于唯一专用网元
```

## 结构关系说明

- T2/T3 主要解决“数据能否在分布式网络中及时可达”；
- T1/T6 主要解决“数据能否被机器正确理解和使用”；
- 两类能力互为条件，工程上可以并行建设；
- T4/T5 只在数据开始驱动真实网络动作时成为关键前置条件；
- T7 的能力型服务不必等待高风险自治成熟；
- T7 的结果型服务额外依赖 T4/T5；
- T8 作用于全部趋势，不构成第五个演进阶段。

## 底部确定性表

| 趋势 | 确定性 | 主要依据 |
|---|---|---|
| T1/T2/T3 | 高 | 需求刚性强，已有较多工程能力 |
| T4/T5/T6 | 中高 | 机制明确，通信级闭环仍需验证 |
| T7 | 中 | 能力服务已有信号，结果型服务尚不成熟 |
| T8 | 低—中 | 标准能力方向明确，最终拓扑尚未收敛 |

## 本页边界

- 不在本页展开每项趋势的技术细节；
- 筛选方法只解释趋势来源，不承担趋势依赖关系的全部论证；
- 不将依赖结构表达为所有产业参与者必须遵循的统一时间顺序。

# 第 2 页｜T2 与 T3：分布式供给基础

## 眉题

> **T2 / T3｜分布式供给基础**

## 主标题

> **元数据事件化与近源执行将共同解决“变化可见、数据按时可达”问题**

## 副标题

> 网络状态持续变化且数据不能默认全量集中，数据控制必须同时具备变化感知、近源处理和断链运行能力。

## 页面布局

```text
┌────────────────────────┬────────────────────────┐
│ T2 元数据事件化        │ T3 全局控制/近源执行  │
│ 定义、范围、触发机制   │ 分层职责、运行流、边界│
├────────────────────────┴────────────────────────┤
│ 领先信号｜验证指标｜反证条件｜外部证据         │
└─────────────────────────────────────────────────┘
```

## 左侧：T2 完整内容

### 趋势名称

> **元数据将从静态目录升级为“变化事件”**

### 机制定义

完整机制不是单纯发送事件，而是：

> **基线快照＋变化事件＋周期对账**

每个变化事件至少携带：

- 事件时间和版本；
- 来源与作用域；
- Correlation ID；
- 受影响的产品、模型、策略和消费者。

### 事件范围

- Schema 和对象关系；
- 拓扑与配置；
- 任务适用性和权限；
- 血缘与成本；
- 数据与模型关联。

### 主要作用

- 自动生成影响清单；
- 触发数据契约测试；
- 使缓存、特征和模型失效；
- 触发策略复核和重新审批；
- 支持跨域变更回放和责任追踪。

### 成立逻辑

1. 静态目录只能描述扫描时刻；
2. 网络配置、拓扑、权限和质量持续变化；
3. 模型和 Agent 使用过期信息可能产生错误动作；
4. 消费者真正需要的是“发生了什么变化以及影响谁”。

### 适用边界

- 不将全部业务数据改造成事件；
- 不让中央事件总线进入毫秒快环；
- 变化事件不能替代本地状态；
- 必须保留基线快照和周期对账。

## 右侧：T3 完整内容

### 趋势名称

> **部署形态将收敛为“全局控制、近源执行”**

### 成立逻辑

1. 高频无线与感知数据不能默认全量远传；
2. 带宽、时延、能耗、隐私和断链形成物理约束；
3. 快环、MEC、专网和 NTN 必须保持本地运行；
4. 完全分散又会造成语义、版本和责任漂移；
5. 因此需要逻辑全局控制与本地确定性执行分层。

### 两级职责

**全局层**

- 对象与语义；
- 任务适用性模板；
- 产品定义；
- 策略、模型和版本发布。

**本地层**

- 过滤、聚合和特征提取；
- 缓存与预编译策略；
- 受限推理和动作；
- 断链期间按已批准版本运行。

**异步回流**

- 数据摘要；
- 执行证据；
- 漂移与冲突；
- 版本回退状态。

### 适用边界

- “全局控制”指逻辑规则一致，不等于所有控制物理集中；
- 远端目录和审批不能成为快环同步依赖；
- 不同网络仍可能采用不同层级和部署拓扑；
- 趋同的是部署约束，不是统一产品名称。

## 底部验证体系

| 项目 | T2 | T3 |
|---|---|---|
| 领先信号 | 变更自动生成影响清单并触发测试 | 近源算子与全局目录、策略解耦 |
| 指标 | 发现 P95、影响覆盖、漏报率、对账差异、传播时长 | P99、字节减量、断链可用、策略同步、版本回退 |
| 反证 | 事故早于目录发现变化，仍依赖人工扫描 | 所有查询和审批必须经过中心 |
| 外部证据 | OpenLineage 等事件模型 | Ericsson、Huawei、Nokia 的两级部署趋同 |

## 页面结论

> T2 解决“变化能否及时传播”，T3 解决“数据和执行能否在物理约束下保持可用”；二者共同构成分布式供给基础。

# 第 3 页｜T1 与 T6：数据运营基础

## 眉题

> **T1 / T6｜数据运营基础**

## 主标题

> **网络数据将由接口资源升级为带契约和适用性证明的运营产品**

## 副标题

> 数据可访问不等于可使用；持续复用需要稳定产品责任，进入模型与闭环还需要面向任务的适用性证明。

## 页面布局

```text
┌────────────────────────┬────────────────────────┐
│ T1 可运营数据产品      │ T6 任务适用性准入       │
│ 产品定义与运营机制     │ 适用性信封与准入机制    │
├────────────────────────┴────────────────────────┤
│ 产品契约如何调用任务适用性｜指标｜反证｜外部证据     │
└─────────────────────────────────────────────────┘
```

## 左侧：T1 完整内容

### 趋势名称

> **网络数据将被封装为可运营的数据产品**

### 产品最低定义

每项产品必须具备：

- 明确消费者与任务；
- 稳定标识和版本；
- Owner；
- Schema 与语义；
- 任务适用性与 SLO；
- 用途与权限；
- 数据血缘；
- 成本与计量；
- 保留期和退出机制。

### 成立逻辑

1. 6G 数据源与消费者数量同时增加；
2. 点对点集成成本随“源 × 消费者”增长；
3. 稳定契约是跨场景复用的必要条件；
4. 无 Owner 就无法持续管理变更、SLO、成本和退出；
5. 无上下文和质量边界的字段交付无法支持机器消费。

### 落地重点

- 优先产品化故障、节能、移动性、QoE 和模型特征；
- 默认交付事件、聚合指标、特征或分析服务；
- 以跨场景复用、持续消费者和单位任务成本验收；
- 不以目录数量、接口数量和数据规模作为主要指标。

### 适用边界

> 只有目录条目、接口包装或 Marketplace 页面，不构成可运营数据产品。

## 右侧：T6 完整内容

### 趋势名称

> **任务适用性将成为数据进入模型与闭环的准入标准**

### 任务适用性定义

任务适用性不是覆盖所有数据的统一质量总分，而是：

> **面向特定对象、时间、配置和任务的数据适用性信封**

> **术语边界：**本计划不再使用 QoD 表示 Quality of Data；QoD 仅指 CAMARA Quality on Demand API。

### 适用性信封

**通用质量**

- 准确、完整、一致、新鲜、唯一、可追溯。

**通信质量**

- 采样代表性；
- 时空覆盖；
- 同步误差；
- 配置一致性；
- 测量置信度；
- suspect/incomplete 状态。

**AI 质量**

- 标签来源；
- 训练—服务分布偏差；
- 特征漂移；
- 适用对象与禁用边界。

### 准入机制

- 不同用途设置不同阈值；
- 未达阈值触发降级、阻断或重新验证；
- 任务适用性与模型卡、产品契约和动作风险挂钩；
- 不同数据族保留各自误差模型。

### 适用边界

- 字段完整不等于语义可比；
- 样本量大不等于具有代表性；
- 不能使用一个全局总分掩盖不同数据族差异；
- 任务适用性尚不是已经冻结的统一 3GPP 指标。

## 底部验证体系

| 项目 | T1 | T6 |
|---|---|---|
| 领先信号 | 产品契约进入版本基线 | 任务适用性进入契约、模型卡和放行条件 |
| 指标 | 复用消费者、交付周期、契约违规、单位成本 | 覆盖、代表性、同步误差、漂移、降级触发 |
| 反证 | 每个场景仍重新取数和清洗 | 仍只统计完整性和接口成功率 |
| 外部证据 | Nokia Data Suite、Ericsson Data Mesh | Huawei Data QoS、Nokia validity、Ericsson 质量主张 |

## 页面结论

> T1 解决“由谁持续提供什么数据”，T6 解决“该数据是否适用于当前任务”；二者共同形成可运营、可准入的数据供给。

# 第 4 页｜T4 与 T5：可信自动化能力

## 眉题

> **T4 / T5｜可信自动化趋势**

## 主标题

> **Agent 协同与 NDT 动作验证将共同构成高风险自动化的可信准入机制**

## 副标题

> 数据进入真实网络控制后，错误不再只是分析偏差，而可能转化为网络、业务和责任风险。

## 页面布局

```text
┌─────────────────────────────────────────────────┐
│ 共用主流程：供数 → 决策 → 验证 → 执行 → 回证 │
├────────────────────────┬────────────────────────┤
│ T4 Agent 协同闭环      │ T5 NDT 动作证据       │
│ 接口、证据、治理责任   │ 快照、预演、门槛、回流│
├────────────────────────┴────────────────────────┤
│ 权限演进｜验证指标｜反证条件｜外部证据         │
└─────────────────────────────────────────────────┘
```

## 共用主流程

1. **供数**：提供产品版本、上下文、任务适用性和用途策略；
2. **决策**：模型与 Agent 选择数据、工具和候选动作；
3. **验证**：执行 NDT 预演、策略校验和风险预算检查；
4. **执行**：按身份、作用域和租约调用执行面；
5. **回证**：将结果、漂移、熔断和回滚写入证据图。

## 左侧：T4 完整内容

### 趋势名称

> **Data Fabric 与 AI/Agent 将形成“供数—决策—执行—回证”协同闭环**

### 融合内容

- 目录检索、订阅、血缘和策略成为 Agent 受控工具；
- 数据、模型、提示、工具、动作和结果共享版本关系；
- 审计证据能够跨工具和执行系统传播；
- Agent 根据当前对象、配置、任务适用性和权限进行决策。

### 保持分离的治理责任

- 数据治理负责用途、保留和删除；
- 模型治理负责性能、偏差和漂移；
- Agent 治理负责身份、权限和动作；
- Reasoner 与 Actor 保持隔离；
- 无边界的统一“大脑”不具备可审计责任结构。

### 落地顺序

1. 只读检索和调查；
2. 决策建议和工单编排；
3. 影子运行；
4. 白名单低风险动作；
5. 高风险动作受控准入。

## 右侧：T5 完整内容

### 趋势名称

> **NDT 预演将成为高风险网络动作的重要放行证据**

### Data Fabric 与 NDT 的关系

- Data Fabric 提供带时间、配置、任务适用性和血缘的状态快照；
- NDT 比较执行、不执行和替代动作；
- NDT 输出收益、冲突和副作用证据；
- 策略系统决定放行、灰度或拒绝；
- 生产结果反向用于孪生模型校准。

### 有效证据条件

- 定义保真度和最大同步滞后；
- 定义场景覆盖和可接受预测误差；
- 保存输入快照、孪生版本、候选动作和预演结果；
- 保存放行理由与生产结果；
- 超过误差门槛时退回建议或人工模式。

### 适用边界

- NDT 是重要证据来源，不是绝对安全证明；
- 不能用“孪生通过”替代责任审批；
- 必须与灰度、熔断、回滚和人工接管组合；
- 快环保留确定性执行。

## 底部验证体系

| 项目 | 内容 |
|---|---|
| 领先信号 | Agent 调用携带身份和版本；NDT 进入变更审批与动作验证 |
| 验证指标 | 证据完整率、越权拦截率、预测误差、人工接管、回滚成功率 |
| 反证条件 | 只有聊天/RAG；无法说明用了哪份数据；NDT 只有拓扑可视化 |
| 外部证据 | 3GPP AI 生命周期、SA5 NDT 管理、厂商 Agent 与自治平台 |

## 页面结论

> T4 建立端到端责任链，T5 提供高风险动作前验证；二者共同决定自动化权限可以扩大到何种范围。

# 第 5 页｜T7：双商业路径

## 眉题

> **T7｜商业化双路径**

## 主标题

> **商业化将分化为“数据/API 能力服务”与“结果型服务”两条路径**

## 副标题

> 两条路径共用可信数据供给，但结果型服务额外依赖可审计、可约束、可回滚的网络行动。

## 页面布局

```text
┌─────────────────────────────────────────────────┐
│ 共同基础：稳定产品、任务适用性、SLA、用途、计量       │
├────────────────────────┬────────────────────────┤
│ 路径 A：能力型服务     │ 路径 B：结果型服务    │
│ 可先行                 │ 条件升级               │
├────────────────────────┴────────────────────────┤
│ 成立逻辑｜商业条件｜指标｜反证｜外部证据       │
└─────────────────────────────────────────────────┘
```

## 共同成立逻辑

1. 外部服务一致性上限取决于内部数据产品稳定性；
2. 内部语义、任务适用性、权限和血缘不稳定，API 只会放大差异；
3. 单运营商覆盖通常不足以支撑规模行业应用；
4. 聚合层需要统一发现、认证、行为、用量和结算；
5. 跨组织使用需要持续执行用途、撤销、责任和收入分配。

## 路径 A：能力型服务

### 供给内容

- Quality on Demand（QoD）、位置、身份和网络状态；
- 网络分析与风险识别；
- 标准化网络能力 API；
- 最小必要、可撤销的数据产品。

### 客户

- 行业平台；
- 应用开发者；
- CPaaS；
- 网络能力聚合渠道。

### 计价方式

- 调用；
- 会话；
- 覆盖；
- 用量；
- 订阅。

### 前置条件

- 内部产品契约；
- 跨运营商行为一致；
- 可追溯的外部 SLA；
- 用途约束与计量结算。

### 关键判断

> 能力型服务不需要等待高风险自动化成熟，可以在 T4/T5 尚未规模化时先行。

## 路径 B：结果型服务

### 供给内容

- 网络体验改善；
- 交易成功率提升；
- 风险和损失降低；
- 能耗、故障率和运营成本改善。

### 客户

- 金融；
- 车联；
- 工业；
- 媒体；
- 其他承担业务结果的行业客户。

### 计价方式

- 效果增益；
- 风险降低；
- 业务量；
- 结果分成。

### 额外前置条件

- T4/T5 可信行动机制；
- 结果归因；
- 动作授权；
- 风险暴露上限；
- 失败回退；
- 责任与收益分配。

### 关键判断

> 结果型服务要求供应方承担动作和效果责任，因此不能由标准 API 直接推导。

## 底部验证体系

| 项目 | 路径 A：能力型服务 | 路径 B：结果型服务 |
|---|---|---|
| 领先信号 | 持续付费和跨网结算 | 动作证据和效果责任进入合同 |
| 指标 | 跨网一致、付费客户、调用收入、履约成本、续费 | 结果归因、误动作、风险暴露、回滚成本、效果分成 |
| 反证 | API 增长但无持续消费者和收入 | 结果无法归因、定责或回退 |
| 证据 | CAMARA、Open Gateway、TM Forum、聚合渠道 | 规模付费、责任和归因公开证据不足 |

## 适用边界

- 原始感知数据出售不是默认模式；
- API 数量不能替代商业验证；
- 内部效率价值不等于外部商业收入；
- 两条路径应分别核算收入、责任和履约成本。

# 第 6 页｜T8：标准承载趋势

## 眉题

> **T8｜标准承载趋势**

## 主标题

> **标准更可能冻结“能力与接口”，而非唯一专用数据面网元**

## 副标题

> 跨厂商必须统一的是外部行为；内部组件、拓扑和部署位置仍可能保持多样化。

## 页面布局

```text
┌────────────────────────┬────────────────────────┐
│ 标准优先固化           │ 实现保持开放           │
│ 能力、语义、接口       │ 功能、组件、拓扑       │
├────────────────────────┴────────────────────────┤
│ 可选落位｜领先信号｜验证指标｜反证条件         │
├─────────────────────────────────────────────────┤
│ 第三章产业结论                                 │
└─────────────────────────────────────────────────┘
```

## 左侧：标准优先固化

- 生产者、消费者和处理能力角色；
- 稳定对象标识、对象关系和信息模型；
- 任务适用性公共属性；
- 数据发现、处理、存储、交付和暴露行为；
- 生命周期、授权和证据引用；
- 跨厂商一致性测试。

## 右侧：实现保持开放

- 增强 DCCF、ADRF、NWDAF 和 MDA 等既有功能；
- 以 SMO 或管理域服务承载；
- 以边缘 Agent 执行近源能力；
- 使用可插拔运行时和多后端；
- 在既有能力无法满足时新增专用网络功能。

## 成立逻辑

1. 发现、采集、处理、存储、暴露和治理跨越多个域与时标；
2. 不同用例无法共享完全相同的在线流程；
3. 标准需要优先统一跨厂商必须一致的外部行为；
4. 固化内部拓扑会增加时延、状态、容灾和迁移成本；
5. 新增统一网元只有在复用既有能力无法满足时才合理。

## 产品与标准策略

- 标准跟踪聚焦能力、语义、任务适用性、接口和测试；
- 产品采用可插拔运行时和多后端；
- 既支持增强既有功能，也支持 SMO 服务、边缘 Agent 或新 NF；
- 若独立平面增加时延和重复治理，应退回能力增强；
- 若复用既有功能导致职责不可分，再考虑新增功能。

## 验证体系

| 项目 | 内容 |
|---|---|
| 领先信号 | Rel-21 收敛能力、信息模型和接口，同时允许多种部署拓扑 |
| 验证指标 | 互操作、复用率、额外时延、状态成本、迁移和替换成本 |
| 反证条件 | 3GPP 冻结独立统一数据平面、必选 NF 和统一流程 |
| 外部证据 | SA2 KI#21、SA5 DMFW、O-RAN 接口及厂商原型 |

## 第三章收束

> **6G Data Fabric 的核心控制点将集中于语义、任务适用性、近源运行、动作证据和跨网结算，而不是单一平台名称。**

## 确定性

> **低—中：能力收敛方向相对明确，最终网元和部署拓扑仍存在较大不确定性。**
