## 2. 胶片的核心任务

2.3胶片不承担“把HTML压缩搬运到PPT”的任务，而要让评委在没有口头交接时，独立理解以下判断：

> 6G数据能力尚未收敛为统一Data Fabric，而是形成三条不同路线；真正趋同的不是平台名称，而是跨域语义、QoD、近源执行和动作证据等控制能力，以及它们的外部接口。

整组胶片只回答四个问题：

1. 为什么同一组6G约束会产生三条不同架构路线？
2. 标准已经划定了什么边界，哪些实现选择仍然开放？
3. Ericsson、Huawei、Nokia分别如何组织数据流、控制流与产品边界？
4. 三条路线最终争夺哪些控制点，如何判断路线是否成立？

## 3. 叙事结构

采用“提出分歧 → 划定边界 → 三家案例 → 归纳结论”的六页结构：

```text
P1 为什么分化
        ↓
P2 标准允许什么
        ↓
P3 Ericsson ─┐
P4 Huawei    ├─ 三种架构选择
P5 Nokia     ┘
        ↓
P6 路线比较 + 四类控制点
```

原2.3.3的三路线比较移至P6作为总结；原2.3.7不再单独成页，其四类控制点和竞合边界并入P6。

## 4. 逐页制作方案

### P1｜为什么会形成三条路线

**页眉编号**

`2.3.1 · ARCHITECTURE CHOICE`

**结论式标题**

> 6G数据能力不会收敛为单一Fabric；三条路线围绕同一组控制能力竞争

**本页目的**

先解释路线分化的原因，避免读者把三家理解为同一成熟度阶梯。

**主视觉**

制作一张“约束—路线—收敛点”架构分化图：

```text
四项共同约束                         三条路线

事实在近源 ─┐                    Ericsson · 存量联邦
语义要跨域 ─┼→ 控制权如何分配 → Huawei   · 网络原生拓扑
少搬运多计算 ┤                    Nokia    · 分层商品化
动作要回证 ─┘

          共同绕不开：语义 / QoD / 近源运行时 / 动作证据
```

**页面布局**

- 顶部15%：标题与一句论点
- 中部25%：左侧四项架构约束
- 中部55%：右侧三条路线卡片
- 底部15%：四类共同控制能力作为横向收敛带

**必须保留的信息**

- Ericsson：连接既有数据岛，以复杂协调换迁移连续性
- Huawei：重构数据拓扑，以新平面复杂度换近源控制
- Nokia：组合数据与自治软件，以分层SKU换产品化速度
- 三条路线是不同起点，不是“谁更接近Fabric”的排名

**不进入本页**

- 厂商组件缩写
- 标准组织清单
- 产品和案例证据
- 逐项能力覆盖表

### P2｜标准划定竞争边界

**页眉编号**

`2.3.2 · STANDARD BOUNDARY`

**结论式标题**

> 标准先冻结外部行为，不会先冻结统一平台

**本页目的**

说明三条路线能够并存的制度原因：标准更关注跨厂商必须一致的对象和接口，不替厂商选择内部拓扑。

**主视觉**

三层能力架构：

```text
外部产品行为       API · SLA · 用途 · 计量 · 结算
                         ↑
跨域控制语义       稳定ID · 最小元数据 · QoD · 授权 · 动作证据
                         ↑
网络权威事实       RAN · Core · OAM · O-RAN接口
```

右侧放置两个判断框：

1. **较可能先冻结**
   角色、稳定标识、最小元数据、交付控制、QoD/授权/证据挂钩点、一致性测试。
2. **仍然保持开放**
   既有NF增强、新NF、边缘Agent、管理侧服务、湖仓、消息运行时及是否存在独立Fabric。

**证据锚点**

- ITU-R需求空间：`[S1]`
- SA2 KI#21：`[S5]`
- SA5管理分析与数据框架：`[S6][S26][S29]`
- O-RAN时标与接口：`[S7]`
- ETSI ZSM 029：`[S43]`
- 外部服务与运营接口：`[S15][S16]`

**不进入本页**

- 七行标准盘点表
- 每个接口的详细职责
- Kafka、湖仓等产品功能比较

### P3｜Ericsson：存量联邦路线

**页眉编号**

`2.3.4 · ERICSSON`

**结论式标题**

> Ericsson以联邦保留存量：迁移连续性最强，跨产品一致性是关键风险

**主图选择**

- 主图：`data-fabric-assets/ericsson-data-ingestion-architecture-2026.svg`
- 辅图：`data-fabric-assets/ericsson-ai-ready-data-management-2026.svg`

Figure 18作为主图，因为它最能证明联邦路线和EDCA/DRG的架构连续性；North Star缩为右上角或图中插页，用于表达治理能力扩展。

**主图标注**

1. **近源摄取仍保留**：EDCA、DRG在2026 Figure 18继续存在。
2. **联邦边界被扩展**：客户侧DMF与Ericsson侧EFDL/Data Fabric连接。
3. **治理范围上移**：North Star增加目录、质量、血缘、语义/KG和数据产品。

**右侧三段分析**

1. **数据与控制如何流动**
   数据在域内采集加工，通过联邦访问和智能移动供跨域消费；目录、策略和治理提供统一视图，执行仍分散在DataOps、NWDAF、EIAP/rApps和域系统。
2. **为什么选择这条路线**
   RAN、Core、OSS/BSS和边缘权威源天然分散，且Mediation、NWDAF、SMO/RIC和客户湖仓不可跳过。
3. **竞争含义**
   优势是渐进接入、多后端和迁移风险低；代价是跨产品Schema、QoD、策略和版本可能长期碎片化。

**底部证据条**

- **已证明**：Figure 18延续EDCA/DRG；Mediation、EIAP、NWDAF等分别有产品或部署锚点。
- **关键边界**：官方产品血缘是 `Mediation → Telco DataOps`，不是 `EDCA → DataOps`。
- **决定性验证**：同一版本化数据产品能否跨DataOps、EIAP、NWDAF及第三方后端复用，无需项目级重写。

**证据锚点**

`[S9][S10][S21][S30][S35][S36][S57][S58]`

### P4｜Huawei：网络原生拓扑路线

**页眉编号**

`2.3.5 · HUAWEI`

**结论式标题**

> Huawei重构数据拓扑：近源执行控制最强，电信级可靠性是验证门

**主图选择**

`data-fabric-assets/huawei-6g-data-plane-architecture.jpg`

**主图标注**

1. **DO**：能力注册、操作DAG分解、选点和策略下发。
2. **DA / DPF / DSF**：在UE、RAN、边缘和Core进行近源采集、处理、推理与存储。
3. **DCP / Data Spine**：以Pub/Sub解耦生产者和多消费者。

**右侧三段分析**

1. **控制流**
   服务意图进入DO，DO选择执行能力、生成数据处理拓扑并下发策略。
2. **数据流**
   源DA发布数据，DCP异步分发，DA/DPF沿途过滤、压缩、特征化和推理。
3. **为什么需要新平面**
   AI/ISAC的多源、多处理、多汇和派生数据链不完全适配围绕控制消息与连接设计的CP/UP。

**底部证据条**

- **原型信号**：DCP公开实验约2ms；10 broker、128KB消息约2,394.6MB/s。
- **比较局限**：DCP移除持久化，而RocketMQ对照开启持久化，不能外推为同功能全面领先。
- **决定性验证**：能否通过同等持久化条件下的跨站故障、移动性、断链回退、多租户SLA和第三方算子测试。

**架构边界**

DO/DA/DCP首先是网络数据面机制。跨域语义、QoD、血缘和产品契约可能被网络原生吸收，也可能由管理域补充；不能把“补成Fabric”设为唯一终点。AUTINOps只证明管理域语义与Agent闭环部署，不证明DCP已经商用。

**证据锚点**

`[S12][S14][S37][S38]`

### P5｜Nokia：分层商品化路线

**页眉编号**

`2.3.6 · NOKIA`

**结论式标题**

> Nokia分层商品化：产品进入现网最快，统一控制与开放性仍待证明

**主视觉**

以自绘五段链路为主，官方AN Fabric图作为右侧证据插图：

```text
域数据底座
    ↓
Common Data Fabric / Lakehouse
    ↓
Data Suite
语义 · QoD · 血缘 · 数据产品
    ↓
AN Fabric / AN Apps
Sense · Think · Act
    ↓
域控制器动作 + API / Marketplace
```

**官方图片**

`data-fabric-assets/nokia-autonomous-network-fabric.png`

**必须讲清的层次**

- Data Suite是数据管理层，与目录、语义、质量、血缘和产品机制直接重合。
- AN Fabric是智能消费与编排层，不是数据管理Fabric的同义词。
- 高风险动作仍通过AN Apps调用OSS/RIC/SON等域控制器。
- 数据默认留域，公共层提供适配、抽象和联邦访问，而非强制集中。

**底部证据条**

- **域应用已证**：KDDI覆盖20万4G/5G RAN；stc披露超过1万次自动动作；Indosat证明节能应用可扩展。
- **数据规模信号**：匿名Tier-1案例披露25万小区、27万报告/秒，仅支持摄取与关联潜力。
- **决定性验证**：Data Suite与AN Fabric是否共享同一契约，第三方后端/Agent能否双向替换，动作与回滚证据能否贯通域控制器。

**证据锚点**

`[S23][S24][S31][S32][S33][S34][S39]`

### P6｜路线比较与最终控制点

**页眉编号**

`2.3.3 + 2.3.7 · SYNTHESIS`

**结论式标题**

> 三条路线不构成成熟度序列；最终胜负由四类接口控制权决定

**上半页：唯一比较矩阵**

| 比较项 | Ericsson | Huawei | Nokia |
|---|---|---|---|
| 架构起点 | 连接既有数据岛 | 重构数据处理拓扑 | 组合数据与自治软件 |
| 控制中心 | 联邦目录、治理与策略 | DO与网络原生拓扑 | Data Suite + AN Fabric分层 |
| 执行位置 | 域内产品与数据湖 | UE/RAN/边缘/Core近源算子 | 域湖仓与OSS/RIC/SON |
| 换取的优势 | 迁移连续性 | 近源执行控制 | 产品化速度 |
| 结构性代价 | 跨产品协调复杂度 | 新平面可靠性与状态复杂度 | 多层SKU与软锁定 |
| 决定性验证 | 跨产品、跨后端复用 | 同功能可靠性和多厂商测试 | 统一契约、动作贯通、后端可替换 |

正式胶片中将文字进一步缩短，但不得删除“优势—代价—验证”三组判断。

**下半页：四类共同控制点**

1. **跨域语义与身份**
   稳定ID、权威源、配置版本和对象映射。
2. **QoD与产品契约**
   用途适用性、Owner、SLO、计量、降级与退出。
3. **近源运行时**
   算子放置、策略下发、断链生存和版本回退。
4. **动作证据与接口**
   数据—模型—策略—动作—结果—回滚的关联、导出与测试。

**路线落点**

- Ericsson争夺联邦目录与渐进治理控制权。
- Huawei争夺数据拓扑与近源运行时控制权。
- Nokia争夺语义产品与自治应用入口控制权。

**最终收束句**

> 真正的平台地位不是把所有数据收到一个平台，而是让跨域消费者遵循自己的语义、QoD和证据契约，同时证明运行时、后端和渠道仍可互操作、可替换。

**竞合边界小字**

设备商更接近网络语义、近源执行与动作权限；云和湖仓更接近规模数据/模型运行时；聚合商更接近跨网分发与结算。三者可以组合，但RAN快环和网元动作权限不能外移。

**证据锚点**

`[S18][S25]`，以及P3—P5所列厂商证据。

## 5. 统一版式规范

### 5.1 金字塔规则

每页严格按以下层次组织：

1. **标题即结论**
2. **架构图或逻辑图解释结论**
3. **最多三项分析**
4. **底部证据与验证门**

`2.3.x`只作为页眉编号，不作为主标题。

### 5.2 信息密度

- P1、P2、P6：约250—320个汉字
- 厂商页：约320—420个汉字
- 每页最多一个主视觉、三个分析块、一个证据条
- 每页最多保留一个高价值数字组
- 全章只允许P6出现比较表
- 参考文献仅保留编号，统一放在页脚或证据条

### 5.3 字体与字号

- 中文字体：`WenQuanYi Micro Hei`
- 主标题：20—22pt，粗体
- 论点框：12—13pt
- 正文：9.5—11pt
- 表格：8.5—9.5pt
- 证据与引用：7.5—8.5pt
- 不得通过小于7.5pt的字号解决溢出

### 5.4 色彩

- Navy：主标题、表头、核心结论
- Teal：架构主线、控制点、正向判断
- Gold/Amber：尚待验证、路线代价
- Coral：停止线和反证条件
- 浅灰：证据条与次级说明

厂商页不使用厂商品牌色主导版面，避免视觉上形成偏向。

### 5.5 图片规则

- 保持原始长宽比，禁止拉伸
- 官方图片必须标注“官方架构/参考架构/研究架构”的证据层级
- 使用编号、半透明框或引线标注关键组件，不在图外重复抄写所有组件
- Ericsson的两张图需要明确区分：
  - Figure 18：架构继承与联邦边界
  - North Star：治理能力扩展
- Nokia官方图只证明AN Fabric智能层；Data Suite与域数据链需要单独自绘
