Deep Research · Composition & Maturity

业界对 Data Fabric 组成为何繁多？当前成熟到哪一步？

本报告独立对照分析师、厂商、学术与产品品牌四类叙事，拆解 Data Fabric「由什么组成」的分歧根源；并在概念成熟度、组件成熟度、组织能力成熟度三个层面评估现状。目标不是再发明一个口号，而是给出可审计的能力清单与成熟度闸门。

研究截点：2026-08 焦点：组成多样性 × 成熟度证据 性质：战略研究参考，非采购背书 方法：公开文献对照 + 能力综合
01 · Problem

为什么「组成」会如此繁多？

Data Fabric 不是单一标准网元，也不是单一可安装软件包。它同时被当作设计概念、平台品类、厂商产品线和组织转型口号使用，四套话语互相借用词汇，却回答不同问题。

概念边界未冻结

Gartner 将其定义为新兴数据管理/集成设计；IBM 强调设计方法而非单一软件；Forrester 则以「统一智能端到端数据平台」评价厂商。同一名词对应不同评价单元。

产品营销扩张边界

集成、虚拟化、目录、湖仓、MDM、治理、Marketplace、GenAI 都被塞进「Fabric」包装。组成清单随厂商优势能力膨胀，而非随最小必要能力收敛。

实证与形式化不足

学术综述与参考能力模型指出：多数架构论文停留在概念层；完整实现与可复现实证很少；组件细节往往不足以判断「同名是否同物」。

关键判断：「组成繁多」本身不是信息噪音，而是信号——说明市场仍处在能力拼装期，尚未进入标准架构期。采购与建设应以「能力是否被证明」而非「清单是否最长」为准。
最实用的拆法是：把任何一份「Data Fabric 组成图」还原为三个问题——它在回答分析师定义、厂商可售能力，还是组织可运营能力？三者混谈，组成必然发散。
02 · Composition Schools

四类组成学派：各自在画什么图？

下列学派并非互斥阵营，而是同一市场中的四种构图方式。理解构图意图，才能读懂清单差异。

A. 分析师学派：以主动元数据为中心的设计

Gartner

公开定义强调：灵活、可复用、增强式数据集成；按定义把被动元数据转化为主动元数据。组成上突出增强目录、图谱分析、推荐/自动化，以及多模式集成。2025 趋势语境中出现「Multimodal Data Fabric」，把编排洞察与 DataOps、数据产品更紧密连接。

Forrester

公开材料给出六层功能：data management、ingest、processing、orchestration、discovery、access。Wave 评估把品类推进为「Data Fabric Platforms」（至 2025 Q4 仍有平台评级），评价维度覆盖端到端体验、语义、GenAI、交付与产品化等。组成更偏「可被买到的平台能力」。

B. 厂商架构学派：可落地的能力模块

IBM

知识目录 / 语义、统一治理与合规、智能集成（批/流/CDC/虚拟化）、自助访问、统一生命周期（含 MLOps）。反复强调「不是一件软件，而是覆盖混合多云的设计方法」。

Informatica

五支柱：增强目录、语义知识图、元数据激活与推荐引擎、数据准备与交付、编排与 DataOps。组成重心落在 CLAIRE 式主动元数据与自动化任务。

Denodo 等虚拟化路线

强调逻辑访问层、目录、隐私与访问控制、消费协议、治理策略管理与数据产品购物车。组成更偏「逻辑编织」，物理湖仓可外置。

C. 产品品牌学派：把平台命名为 Fabric

Microsoft Fabric / OneLake：以租户级 OneLake、工作区、Lakehouse/Warehouse/Eventhouse 等工作负载，以及 OneLake Catalog、Shortcuts/Mirroring 构成统一分析平台。它是高强度产品化的「Fabric」品牌，能力完整且可运营，但不宜直接等同于 Gartner 意义上的跨异构主动元数据设计；评估时必须区分「品牌同名」与「架构同构」。

D. 学术 / EA 学派：能力参考模型与边界划定

DFA-RCM（Oostrik, 2025）

以 ArchiMate 能力图形式给出 Data Fabric Architecture Reference Capability Model，并提炼 Core Capability Set（CCS）。对 8 份架构文献做组件流行度统计，指出完整实现极少、形式化不足。

概念划界研究（2024–2025）

把 Fabric 与 Platform、Space、Mesh、Lakehouse 放在治理集中度 / 主权维度上比较：Fabric 常被描述为「数据可分布、访问与治理相对集中协调」的混合位置；Mesh 更偏组织去中心；Lakehouse 更偏存储集中。

为什么四派会画出不同的「组成」？

分歧来源表现对读者的误导纠偏问法
评价单元不同 有人评「设计原则」，有人评「可采购平台」，有人评「组织转型包」 把 Wave 排名直接当成架构正确性证明 这份组成图的评价对象是设计、产品还是组织？
历史路径依赖 集成厂商从管道长出 Fabric；虚拟化厂商从逻辑层长出；云厂商从湖仓长出 把「我擅长的模块」写成「Fabric 的必要模块」 若去掉该厂商优势模块，是否仍可称为 Fabric？
中心化叙事冲突 有文献称 Fabric 偏集中治理；有厂商强调分布不搬迁；Mesh 拥趸批评其中心化 在「集中 vs 分布」二元里站队，忽略协调/执行可分离 协调在哪里集中？执行在哪里分布？
时间切片不同 2019 构图偏目录+图谱+增强集成；2024–2025 构图叠加产品、可观察、GenAI 用最新营销清单要求存量平台「一次齐套」 哪些是 2019 核心，哪些是近年加项？
语言通胀 active metadata、intelligent、autonomous、AI-ready 被广泛复用 把 UI 推荐气泡等同生产级闭环 元数据事件能否改变跨系统行为并留下审计？

一条演化时间线：组成清单如何变长

2019 前后
Gartner 早期愿景把元数据目录、语义知识图、主动元数据、动态集成与自动化编排推到台前。组成相对「瘦」，中心问题是：如何用元数据降低集成手工。
2020–2022
治理、虚拟化、Data-as-a-Service、MDM、DataOps、自助访问被显式写入厂商与咨询架构。Forrester 以六层功能与 Wave 评估把 Fabric 推进为可比较品类。
2023–2024
数据产品、Marketplace、可观察性、开放 Catalog/契约进入主流叙事；与 Mesh 的「互补而非二选一」成为常见口径。
2025–2026
GenAI/LLM、语义集成、Agent 辅助、Multimodal Data Fabric 等词汇叠加；平台 Wave 继续存在，但「组成完备」与「企业可运营」之间的落差被学术与实践同时指出。

三种「看起来都叫 Fabric」的实现骨架

骨架 1：元数据控制面优先

以增强目录 + 图谱 + 推荐/自动化为中枢，向下驱动多模式集成与策略。Gartner/Informatica 叙事接近此骨架。优点是贴近「主动元数据」定义；风险是若推荐无法落地为受治动作，会退化为智能一点的目录。

骨架 2：逻辑访问层优先

以虚拟化/联邦查询为统一入口，叠加目录、策略与消费协议。Denodo 类路线接近此骨架。优点是少搬迁、快见效；风险是源系统负载、跨源性能与复杂变换仍可能迫使物理管道回流。

骨架 3：统一分析平台优先

以湖仓/OneLake 类统一存储与多引擎混合为底座，再补目录与治理。Microsoft Fabric 品牌接近此骨架。优点是工程内聚、体验完整；风险是「平台内统一」不等于「企业全异构统一」，跨云/跨厂商仍要额外编织。

选型含义：三套骨架可以组合，但不应在一份 RFP 里要求「同时以三者为唯一中心」。先选定主骨架，再把另外两者降为补充能力，组成争论才会收敛。

04 · Synthesis

综合参考组成：核心、常见扩展、营销膨胀

综合分析师定义、厂商模块、学术 CCS 与流行度统计，本文提出「可审计」的三层组成观。它不是新标准，而是用于过滤清单的工作框架。

CORE

最小核心（缺一难称 Fabric）

① 元数据获取—组织—访问；② 策略定义与强制；③ 跨源连接；④ 至少一种逻辑或物理集成交付；⑤ 受治理的消费访问。学术 CCS 将其概括为「元数据驱动的分布式受治访问」。

COMMON

高频扩展（按场景启用）

主动元数据分析与推荐、语义知识图、批/流/CDC 多模式、编排与 DataOps、质量监测、自助准备、MDM、数据产品/Marketplace、可观察性与成本优化。

INFLATED

易膨胀项（需单独证明）

「统一替换全部湖仓」、厂商全栈独家、完全无人自治、把 GenAI 聊天框等同主动元数据、把 Mesh 组织改革打包进 Fabric 采购合同。

六层 + 横切：本文统一的组成参照架构

面对业界繁多的组成清单，本文不再另起一套「组件名录」，而是把前述核心/扩展能力收敛为六层能力栈 + 一道横切保障的参照架构。它是分析与沟通框架，不是正式标准，也不要求采购单一厂商全栈。

如何读这张分层图：L1–L3 回答数据「在哪里、如何被集成与执行」；L4 是把被动目录变成可推荐/可执行控制面的分水岭；L5–L6 回答数据「以何种产品形态被发现、消费并转化为行动」。横切保障贯穿每一层的访问、质量、安全与可运营性。后文的组件成熟度观察与分层深潜验收，均严格按本架构逐层展开，不再平行引入第二套分类。
L6
消费与行动分析报表 · 接口服务 · 笔记本 · 检索增强 · 智能体 · 运营应用
L5
数据产品与自助数据市场 · 数据契约 · 语义指标层 · 服务水平目标 · 成本可见

主动元数据控制面数据目录 · 血缘 · 知识图谱 · 策略 · 推荐 · 自动化

身份认证 · 数据质量 · 安全隐私 · 数据驻留 · 审计 · 可观察性 · 成本运营
L1

分布式权威源

企业真实产生与持有数据的位置。Fabric 的前提是承认源长期异构分布，而不是先假设「全部搬进一个湖」。本层解决的是权威归属与可达性，不负责统一语义。

典型组件：业务事务库、文件与对象存储、事件流、边缘/设备数据、合作伙伴与外部数据空间连接点。
L2

运行时与存储节点

为分析、特征、检索与近源计算提供执行与持久化能力。湖仓、数仓、向量库等是 Fabric 可连接的节点，不是控制面本身；可以有一个，也可以有多个。

典型组件：数仓、湖仓、特征库/向量库、图数据库、隐私增强技术与可信执行环境。
L3

集成、编排与查询

决定数据如何按需移动、复制、虚拟访问或流水线交付。成熟标志不是「只用虚拟化」或「只用批处理管道」，而是能依据时延、成本、源负载与驻留，在多模式间做可解释选择，并由编排固化。

典型组件：批处理/ELT、变更数据捕获、流处理、数据虚拟化/联邦查询、工作流与作业编排。
L4

主动元数据控制面

整张编织的「神经系统」。采集技术/业务/运营/使用元数据，建立血缘与语义关系，检测变更与异常，进而推荐或执行集成、质量、安全与发布动作。没有 L4 的主动闭环，上层目录与下层管道只是工具拼盘。

典型组件：增强数据目录、血缘、知识图谱/本体、策略引擎、推荐与自动化动作。
L5

数据产品与自助

把可复用输出包装为有责任人、契约、语义与服务水平的数据产品，并通过市场/自助流程被发现与申请。本层解决「找得到、信得过、可复用」，避免消费者直接依赖隐式表名口头约定。

典型组件：数据市场、数据契约、语义/指标层、服务水平目标、成本与价值可见性。
L6

消费与行动

人、应用与智能体真正使用数据并产生决策或闭环动作的界面。成熟度不仅看「能查到数」，还看答案是否可追溯到产品与策略，以及智能体/自动化是否仍受 L4 与横切约束。

典型组件：分析报表、接口服务、笔记本、检索增强生成、智能体编排、运营控制应用。
横切

贯穿式保障（非第七「业务层」，而是约束面）

身份、质量、安全隐私、驻留、审计、可观察与成本运营不属于某一层的可选插件，而是每一层交付时必须满足的约束。策略可在 L4 定义，但必须在 L3/L5/L6 的访问路径上强制生效。

典型组件：身份与权限、数据质量规则、脱敏/加密与用途控制、驻留与保留、审计追踪、管道/查询可观察性、成本运营。

与相邻范式的组成边界

范式组成重心与 Fabric 的关系
Lakehouse开放表格式 + 统一分析引擎 + 事务/治理表能力常是 Fabric 可连接的一个或多个运行时节点，不是控制面本身。
Data Mesh领域所有权、数据产品、自助平台、联邦治理组织/运营模型；Fabric 可作其技术底座，但不自动完成领域责任制。
Data Space跨组织身份、合同、连接器、用途控制企业 Fabric 向外延伸时的信任与协议层。
知识图谱实体—关系—本体语义层关键技术；不能单独承担集成、编排与访问控制。
集成 iPaaS / ETL连接器与管道执行数据面执行器；缺全局语义、用途策略与主动闭环时仍非 Fabric。

学术 CCS：什么被专家视为「不能不做」

DFA-RCM 通过文献流行度与专家访谈收敛出 Core Capability Set。其主张值得单独强调：多位专家认为 Data Fabric 的本质接近「元数据驱动的数据虚拟化」——在混合/多云分布景观中访问数据，而不必然先把数据中央化。

CCS 包含

Data Policy Management；Metadata Acquisition / Management / Access；Connectivity Management；Virtual Data Integration；Data Access。这些能力共同保证：找得到、连得上、逻辑上用得了、策略上控得住。

CCS 之外仍常见但不「核心」

物理集成、编排优化、Marketplace、MDM、可观察性、Agent 管理等被模型收录，却未全部进入 CCS。含义是：它们能显著提升价值，但缺少其中某几项，并不自动否定「你在做 Fabric」。

对战略团队的用法：用 CCS 做「准入门槛」，用扩展清单做「场景增益」。这样可避免 RFP 变成「把所有学派的组成取并集」。
05 · Maturity

当前成熟度：三个层面分别看

「Data Fabric 成熟了吗？」是坏问题。应拆成：概念与品类是否稳定；六层 + 横切参照架构中各层能力是否可用；组织是否具备可验证的运营闸门。后两者共用同一套分层，不另建组件分类。

层面一：概念与品类成熟度

中等成熟

概念：新兴设计，尚未标准冻结

Gartner 仍将其表述为 emerging design；学术论文确认「共识不足」是企业架构师的真实痛点。尚无 ISO/ITU/3GPP 意义上的单一 Data Fabric 产品标准。概念可用于沟通，不可直接当作合规对象。

相对成熟

品类：已有分析师平台评级

Forrester 从 Enterprise Data Fabric Wave（2022/2024）演进到 Data Fabric Platforms Wave（2025 Q4），说明买方市场已形成可比较的平台品类。但这衡量的是厂商平台完整度，不等于企业落地成熟度。

层面二：按「六层 + 横切」观察的技术成熟度（2026）

下表与组成参照架构一一对应：每一行是一层（或横切）的行业能力水位，而不是另开一份「热门组件榜」。阅读时应连同上一节各层说明一起使用。

分层本层关注的能力成熟度证据信号主要风险 / 落差
L1 分布式权威源 多源连接、权威归属、混合/多云/边缘可达 高 连接器与源接入工程成熟；异构并存已是常态 权威源不清、时间语义混乱时，上层再强也会「编织噪声」
L2 运行时与存储节点 数仓/湖仓/特征与向量等执行节点 高 湖仓与开放表格式广泛落地；多引擎共存常见 把单一湖仓误认为完整 Fabric；节点内治理≠跨节点控制面
L3 集成、编排与查询 批处理转换、变更捕获、流、虚拟化、编排 中高—高 多模式集成工具链成熟；虚拟化/联邦长期可商用 管道烟囱化；模式选择缺元数据依据；源负载与一致性风险
L4 主动元数据控制面 目录、血缘、图谱、策略、推荐、自动化 中（落差最大） 被动目录/血缘基线强；推荐与影响分析可见 停在「能搜」；跨系统动作、护栏与 ROI 证据不足
L5 数据产品与自助 数据市场、契约、语义指标、SLO、成本可见 中低 内部商店与契约规范试点增多；术语表常见 有货架无契约；跨域语义运营弱；复用/退出机制缺失
L6 消费与行动 报表/接口/检索增强/智能体/运营闭环 中（智能体偏低） 传统消费成熟；检索增强与助手快速普及 答案难追溯到产品；智能体受治执行与责任边界仍弱
横切保障 身份、质量、安全隐私、驻留、审计、可观察、成本 中（路径一致性弱） 单平台权限/脱敏/监控常见；策略即代码在扩展 SQL/API/导出/向量等多路径强制不一致；用途与删除传播难
读表结论（仍属同一体系）：L1–L3 整体更「可买、可建」；真正把拼盘升级为 Fabric 的瓶颈集中在 L4 主动化、L5 产品化 与 横切多路径强制。L6 的智能体能力应视为建立在 L4/横切之上的加速层，而不是绕过它们的捷径。
实证边界：Oostrik 指出，在其审查的架构文献中，仅少数描述真实实现，完整 Fabric 实现声称更少。Gartner/咨询材料中的「访问准备时间下降 40–60%」等收益数字多见转述，应视为厂商/咨询主张，需用本组织基线复测，不可直接当作行业统计事实。

层面三：组织能力成熟度模型对照

组织侧成熟度模型同样多元。共同点是：从被动目录/手工管道，走向元数据激活与有界自动化；差异在维度切分与级数命名。

模型来源结构对 Fabric 的含义局限
Gartner 数据集成成熟度（L1–L5） L5 = Augmented：激活元数据驱动 ML/AI；并明确 data fabric design 是 L5 要素之一 把 Fabric 锚定在「增强式集成」终点能力，而不是入门项目 偏集成职能视角，组织/产品运营维度较弱
LTIMindtree FABMAT 分阶段能力叠加：评估策略 → 数据管理 → 摄入与知识图 → Marketplace → 洞察 强调用例驱动、小步构建 公开材料偏方法宣传，独立验证有限
实践向五级模型（如 datafabric.cloud 等） 通常覆盖战略、集成、元数据、治理、质量、自助、可观察 等 6–8 域 × 5 级 便于内部打分与对标 非权威标准；域权重需按行业裁剪
本文综合闸门 G0–G5 边界词汇 → 只读可观察 → 产品契约 → 影子闭环 → 有界自治 → 跨域供给 强调证据与风险预算，抑制「跳级自治」 分析框架，需映射到组织 KPI

本文建议的组织成熟度闸门（G0–G5）

G0

边界与词汇

场景目标、Owner、对象语义、权威源、保留期明确。没有 G0，目录只会固化混乱。

G1

只读可观察

关键源接入；Schema、事件时间、血缘、QoD 可查询。先证明「哪份数据对应哪个状态」。

G2

产品与契约

高频输出产品化；契约进 CI；复用可度量；无人使用的资产退出。

G3

影子闭环

系统建议对照人工与结果；高风险动作先沙箱/孪生。主动元数据开始改变决策质量。

G4–G5

有界自治 → 跨域

白名单低风险自动执行；熔断与回滚齐全后再谈跨域最小必要供给。

行业落位的总体判断（2026）

多数企业
停留在 G1 附近：有目录与若干集成平台，但元数据多为被动；跨工具策略不一致；「Fabric」常等于采购叙事。
领先实践
进入 G2–G3：数据契约、开放 Catalog、影响分析、受治自助与部分推荐自动化跑通；仍少见生产级全面自治。
厂商平台
品类成熟度高于平均企业落地成熟度：Wave 中的 Leaders 展示端到端能力，但客户要自己补齐语义责任、组织机制与场景 ROI。
前沿探索
G4 有界自治与 Agent 操作面、跨组织 Data Space 接入并存；证据密度低，适合受控试点，不适合作为全面承诺。

成熟度错位：最常见的四种自欺

1. 用平台 Wave 分数代替组织闸门

买到 Leaders 象限产品，只证明供应商能力包较完整，不证明本组织已达 G2/G3。合同签字≠血缘覆盖，更≠契约复用。

2. 用目录覆盖率代替主动元数据

资产入湖/入目录是 G1 信号。若 schema 变更不会触发影响分析、测试闸门或策略复核，则仍属被动元数据阶段。

3. 用 AI 演示代替有界自治

自然语言查数、自动映射建议属于辅助生产力。一旦涉及授权变更、删除传播、生产控制，缺少熔断/审批/回滚就不能计为 G4。

4. 用组成清单长度代替场景闭环

清单越长越像「齐全」，却可能稀释 Owner 与 KPI。成熟组织通常先在 1–2 个高复用场景打穿 G2/G3，再扩展组成面。

分行业的成熟度差异（观察性判断）

场景类型常见主骨架相对成熟点相对薄弱点
大型银行 / 保险 治理 + 目录 + 集成/虚拟化 策略、分类、审计、MDM 基础较好 跨域语义协商慢；主动自动化受合规约束
互联网 / 数字化原生 湖仓 + 流批 + 平台工程 管道、观察性、自助效率高 企业级语义与用途治理未必系统化
制造 / 运营商类 多源接入 + 近源处理 + 管理数据 实时/准实时集成需求清晰 OT/IT/管理域语义割裂；跨厂商元数据难统一
公共部门 / 跨境协作 Data Space 协议 + 内部 Catalog 主权、合同、用途控制议题靠前 内部 Fabric 与外部空间的互操作成本高

上表为公开叙事与项目经验的综合观察，不是抽样统计结论；用于提示「成熟度必须按约束裁剪」，避免用单一行业标杆要求所有组织。

06 · How to Assess

如何评估一份「组成方案」与「成熟度声称」

面对繁多组成图，评估应坚持：先核心后扩展、先证据后愿景、先场景后平台。

组成方案六问

1. 主动元数据是否能触发跨系统动作，还是仅展示？
2. 集成是多模式可选，还是被单一教条绑定？
3. 策略能否在访问路径强制，而非文档宣示？
4. 语义责任人是否明确（机器建议 ≠ 领域裁定）？
5. 数据产品是否有契约、SLO 与退出机制？
6. 哪些项是本场景必需，哪些是厂商赠送清单？

成熟度声称五问

1. 声称落在六层 + 横切的哪一层（而非另起组件名）？
2. 有无基线与对照（时间、成本、事故、复用）？
3. 自动化覆盖的是低风险建议还是高风险变更？
4. 横切策略在多访问路径上是否被抽检？
5. 若去掉品牌名「Fabric」，该层能力是否仍成立？

最小充分性：何时值得按 Fabric 建设

建议阈值：若同时满足「异构来源长期共存、跨域复用频繁、语义冲突显著、治理约束复杂、变更影响难追踪」中至少三项，并且已有明确场景、Owner 与可量化结果，再进入 G0。否则优先解决最窄瓶颈（口径、权限、单条关键管道或责任人），避免预付控制面复杂度。

建议跟踪指标（与闸门对齐）

G1+

新鲜度 P95、完整率、血缘覆盖、变更发现时延

G2+

产品复用率、重复采集下降、契约合规率

G3+

建议采纳率、误报率、影子对照偏差

G4+

自动动作成功率、回滚耗时、无效动作率

90 日诊断路径（可落地）

Day 0–15
构图审计：收集现有「Fabric」架构图/采购材料，标注每项属于 CORE / COMMON / INFLATED；识别主骨架（控制面 / 逻辑访问 / 统一平台）。输出一页「组成分歧表」。
Day 16–45
证据抽样：选 2 个高价值数据链路，实测目录是否被动、策略是否强制、变更是否可影响分析、复用是否发生。对照 G0–G2 打分，禁止只看工具清单。
Day 46–75
缺口排序：按「场景损失 × 修复成本 × 风险」排序。优先补 CCS 缺口与 G1/G2 指标，而不是先上 GenAI 或 Marketplace 门面。
Day 76–90
目标态裁剪：给出 12 个月组成目标（必须有 / 可以后补 / 明确不做），并设定 G2 或 G3 的可验证出口条件。同步明确语义 Owner 与升级路径。

给架构评审的一句话标准

若一份方案不能说明元数据如何变成动作、策略如何在访问路径强制、哪个场景在何闸门退出，则无论组成图多完整，成熟度声称都应降级处理。
07 · Layer Deep Dive

分层深潜：沿同一参照架构做验收

本节不引入新的组件分类，而是对「六层 + 横切」逐层给出存在 / 可用 / 主动（或强制）三档证据。与层面二的成熟度表配套使用：表看行业水位，这里看本组织如何验收。

L1 分布式权威源

业界现状（映射层面二·L1）

多源接入工程成熟；瓶颈很少是「连不上」，而是权威源、事件时间与保留策略未定义，导致后续血缘与质量无法解释。

验收口径

存在：关键源可连接。可用：每类对象有权威源与 Owner。主动：源变更（下线/换主/时钟漂移）能被控制面感知并进入影响清单。

L2 运行时与存储节点

业界现状（映射层面二·L2）

数仓/湖仓/向量等节点可商用且演进快。常见误判是把「已建成湖仓」等同「已建成 Fabric」——节点解决存储计算，不自动提供跨源主动控制。

验收口径

存在：场景所需节点可用。可用：节点纳入统一标识与成本可见。主动：节点侧 schema/权限/表变更回流 L4，而非孤立运维。

L3 集成、编排与查询

业界现状（映射层面二·L3）

批、变更捕获、流、虚拟化均可落地；成熟标志是多模式可解释共存，并由编排与元数据选择，而不是教条单一路径。

验收口径

存在：至少一种稳定交付路径。可用：关键链路可观测、可重跑。主动：模式选择/切换留下运营元数据；重复管道可度量下降。

L4 主动元数据控制面

业界现状（映射层面二·L4）

目录与血缘基线强；推荐/影响分析可见；跨平台自动修复与高风险自动执行仍弱。这是「拼盘 → Fabric」的主落差层。

验收口径

存在：关键资产可检索。可用：Owner、结构、血缘完整。主动：结构/权限/质量变化在约定时延触发影响分析或闸门；自动化区分建议 / 低风险执行 / 高风险执行。

L5 数据产品与自助

业界现状（映射层面二·L5）

数据市场与契约规范在试点；术语表常见，跨域语义运营稀缺。无契约、无退出的「上架」只是新的影子目录。

验收口径

存在：有可申请的产品入口。可用：产品含 Owner、语义版本、质量目标、许可用途、SLO。主动：契约进持续集成；复用率与违规率可测；长期无消费者则退出。

L6 消费与行动

业界现状（映射层面二·L6）

报表与接口消费成熟；检索增强与智能体快速普及，但受治执行刚起步。智能体是加速器，不能替代 L1–L5 与横切的可信基础。

验收口径

存在：场景消费者可取数。可用：结果可追溯到数据产品与策略。主动：助手/智能体仅在最小权限与审计下执行低风险动作；高风险保留人工接管。

横切保障

业界现状（映射层面二·横切）

单平台身份、脱敏、监控常见；难点是同一敏感字段在查询、接口、导出、向量检索等路径上策略一致，以及撤销/删除的端到端生效。

验收口径

存在：有统一身份与基础审计。可用：质量/安全规则绑定到资产。强制：多路径抽检结论一致；撤销与删除传播时间可测；成本与新鲜度进入运营看板。

与组织闸门的衔接：G0–G1 主要夯实 L1 + L4（被动可用）+ 横切基线；G2 拉起 L5；G3–G4 要求 L4 主动化并约束 L6 行动面。不要用 L6 的智能体演示证明 G4。
08 · Limits

证据缺口与误判风险

组成「最大公约数」仍在形成

目录、虚拟/物理访问、治理是强共识；Marketplace、可观察性、Agent 仍在快速写入清单，明年的「标准组成」可能再次位移。

缺少可比的横向实证

公开成功案例多为单厂商故事；跨组织、跨工具的对照试验稀缺。成熟度自评容易乐观。

同名产品不等于同构架构

Microsoft Fabric、厂商 Intelligent Data Fabric、咨询公司参考架构图，可能共享词汇而共享很少机制。评估必须下钻到元数据事件、策略强制与集成模式。

09 · Conclusion

结论：如何在「组成繁多」中做决定

关于组成

业界繁多不是因为存在很多互不兼容的真理，而是因为分析师设计、厂商平台、产品品牌与学术能力模型在用同一词汇回答不同问题。可操作的收敛方式是：承认三种实现骨架，把能力映射到统一的六层 + 横切参照架构，守住核心集，按场景增益扩展。

关于成熟度

2026 年沿同一分层看：L1–L3 更「可买可建」；瓶颈在 L4 主动化、L5 产品化与横切多路径强制；L6 智能体是加速层。组织侧多数在 G1，领先到 G2–G3；G4 仍属受控前沿。成熟度按层验收 + 闸门证明，而不是另列组件榜或比拼组成图长度。

决策口诀：一张分层图贯穿组成与成熟度；先定主骨架，再按 L1→L6/横切补齐；先拿 G1/G2 证据，再谈 G3/G4 自动化。凡不能说明「落在哪一层、如何验收、元数据如何变成动作」的方案，都应降级。
